# Owned conversation store (typed encounters in the vault)

What the vault engine (`chat/vault/vault.mjs`, `vault-db.mjs`, `vault-store.mjs`) does so that one encounter conversation is kept under the key of the chat (or standalone encounter) that owns it, is committed with its chat in one atomic step, and is destroyed with it. This is the **engine component only**. No feature producer is wired to it, no host, UI, import, backup or file format uses it, and nothing here is a release, a snapshot or a mode decision. Status of the open gates is at the end.

## Representation

* **Typed owned entities, one per encounter.** An entity has an id `E`, an owner and a value `V` (`{format:1, encounter, participants, events, holders}`, complete, unknown fields kept inside their records). The engine treats `V` as opaque JSON except for the checks below. Nothing is put in ordinary thread fields or in the global key-value ledger.
* **Owners.** A local encounter is owned by its chat (`{type:"thread", id:T}`, key `c:T`); `V.encounter.thread` must equal `T`. A standalone encounter is owned by itself (`{type:"encounter", id:E}`, key `e:E`); `V.encounter.thread` is `null`. There is no fake chat or document. The owner comes from the plan the engine validated against stored state, never from a source package.
* **Events** (semantic header 2): `owned.put` and `owned.del`, sealed under exactly the owner's key id. Replay is given the authenticated scope: a record under any other key, an owner whose generation is not the live one, an unknown kind, or an attempt to rebind an existing entity to another owner is refused and marks the log unsupported (so it is never compacted away).
* **Generations.** `key.put` may carry `generation:G` (128 random bits, base64url). The engine makes it for every typed owner; the generic `append` route refuses an owner `key.put` only WHILE typed records or a pending operation exist (`typed-hold`), so with no typed data the generic route still accepts a caller-chosen generation (older behaviour, not typed-specific; a producer must never use it). `key.destroy` removes the key record, its generation and everything it owned; a `key.put` of the same id with a different generation does the same. A same-id chat created again gets a new raw key and generation and never sees the old scoped state. A legacy key without a generation gets one on first admission by reissuing the **same raw bytes** and every recorded field (no rotation, no recovery of a destroyed key).
* **State.** `keyGenerations`, `keyRecords` (the complete `key.put` events) and `encounters` beside the existing maps. `eventsFor` (compaction) emits keys with generation and metadata first and each entity under its owner key, never under the vault key.
* **Index.** One engine-internal key in the log, `meta/encounters.index.v1`, sealed under the vault key: `{v:1, logical:{v,rev,epoch}, revision, entities:[{id,owner:{type,id,generation}}], pending:null|{id,baseRevision}, committed:null|{id,baseRevision,revision}}`. No text, label or payload digest. It is not a browser storage key (listed as `vaultInternalKeys` in the storage inventory). Generic writes of it are refused.
* **Header.** The semantic header `plc-vault/2` is separate from the encryption (AAD and wrap) domain `plc-vault/1`, which is unchanged (`VAULT_FORMAT`). The IndexedDB schema stays 1. Both supported semantic formats are accepted by passphrase unlock, known-key unlock and compaction (each also checks the header stored at that moment); anything else is refused. Typed records under a semantic-1 header are refused.

## The one commit: P1, P2, P3

`session.readChatProjection({guard})` returns `{threads, order, owners, encounters, index, base}`: freshly read, cloned (no aliasing of live state, so a later lock cannot change a snapshot), and a frozen `base` that only the engine can make: it is bound to this session, this adapter and the exact stored header and log. `owners[].generation` is `null` only for a live legacy key, and only inside that base.

`session.commitChatProjection(plan, {guard})` owns every phase inside the engine queue. The guard and a JSON clone of the plan are captured at the call, before the queue; the base keeps its identity; a later change to the plan or the options substitutes nothing. `plan = {base, operationId, threads:{put,create,remove,order}, encounters:{put:[{id,owner:{type,id[,generation]},value}],remove:[{id,owner}]}, standalone:{create:[E],destroy:[{id,generation}]}, logical:{v:1,rev,epoch}}`. A thread or standalone owner is created only when the plan says so (a standalone create must carry its own first entity `E` owned by `e:E`; an orphan owner is refused); an absent owner is never recreated by an update. A `generation` given for an existing owner (`null` included) must be exactly what the base observed (a string is the live generation; `null` means only a live legacy key); for a new owner none may be given.

Everything is validated against the freshly read state before the first write (stale or foreign base, unsupported adapter, pending operation, unknown owner, owner/record mismatch, duplicate ids, unknown root field in `V`, holder prefix, participants or events of another encounter, an order that does not cover exactly the remaining threads); a refusal there is `status:"not-written"` with the stored header and log byte for byte unchanged.

* **P1** appends only `pending={id:P,baseRevision:X}` to the index (current revision, logical counters and last committed receipt kept). The header does not change. It is read back and the payload is compared unchanged.
* **P2** appends, in one transaction with the header: new keys (with generations), the reissued legacy keys, thread, owned and order records, the index with revision `Y` and `committed={id:P,baseRevision:X,revision:Y}` (pending still `P`), and the header `plc-vault/2`. It is read back and the complete state is compared with what was staged.
* **P3** clears only this pending, compared against the exact pending(P,X) and committed(P,X,Y), revision Y and header/log. It is read back.
* Result: `{status:"committed", id:P, operationId, revision:Y, base}` only for a verified, settled result under live authority. Otherwise `not-written` (reason; before any record), `not-committed` (P1 durable, P2 refused whole; pending kept), `unsettled` (P2 durable, P3 not) or `unknown`; the original id is kept and the session then **needs reconcile**.
* The caller never writes the index, supplies phase receipts or chooses a generation.

### Atomic adapter seam

`replaceLog({add, removeUpTo:0, guard, expected:{header,log}, nextHeader})`. The IndexedDB adapter uses one readwrite transaction over `header` and `log`: both are read, compared in the callback of the last read, and `header.put` plus every `log.add` are placed in that same callback with no await or crypto between; the guard is asked at the open, at the transaction's activity, in the final compare-read callback and immediately before the mutation. A failed comparison, request or guard aborts both. The memory twin clones and validates both and publishes both. Both adapters advertise `atomicProjection:true`; an adapter without it makes the commit refuse before anything is written (no sequential fallback). Plain `replaceLog` (compaction) keeps its old contract.

### Uncertainty and reconcile

An adapter error that does not prove an abort, a lost completion, or a durable write whose authority ended marks the session `needsReconcile`: no append, setKv, compaction or new commit runs and no sequence number is reused (no blind rollback) until `reconcileChatProjection({guard})` has replayed the stored header and log under a live guard. It settles a verified P2 (matching committed, revision Y, consistent projection), abandons only a noncontent pending that is provably P1 only (revision still X, no committed for it, projection consistent), reports `clean`/`committed`/`abandoned`, and returns `unresolved` for a pending that belongs to someone else or evidence that no longer proves an outcome. A delayed settlement never clears a newer pending. After a lock or lost authority the durable data stays and live memory is not repopulated.

## Generic routes and the legacy facade

* The generic engine routes refuse reserved writes (`owned.*`, the index key) and, while typed encounters or a pending operation exist, every whole-chat change (`thread.put/del`, chat key `put/destroy`, the thread order, `delThread`) with `typed-hold`, before any record is sealed or written. Unrelated settings and documents are unaffected. Compaction refuses while an operation is pending. Compaction also refuses on a locked session and whenever its guard stops authorizing (asked when it starts, again at the boundary where the log is replaced, and by the adapter where it is replaced), with `locked` or `session-changed` and no sequence number used: a locked session would otherwise replace the stored log with an empty state and lose every record (`tests/vault-header-rewrite.test.mjs` (a header rewrite racing a typed commit never downgrades the header), `tests/vault-transition-busy.test.mjs` (`app.transition` refuses a call made while another runs and never queues it), `tests/vault-typed-actors.test.mjs` (separate processes racing one backend), `tests/helpers/vault-typed-kill-idb.mjs` (a real browser, a real SIGKILL), `tests/vault-compact-guard.test.mjs`). A real delete or Clear of typed chats goes through the typed commit (thread removal destroys the owner key, which purges what it owned); aware consumers wire that later.
* `vault-store.mjs`: `setItem`/`removeItem`/`clear` of `chatThreads` are refused before the optimistic mirror, thread JSON or queue are touched while the session reports a typed hold (event `plc:vault-held-write`, reason `typed-encounters`). The same barrier covers ordinary writes: when an append fails without a known abort code, the engine reads the stored log; only a successful read that shows no record with that seq gives the seq back, otherwise the seq stays used and the session needs reconcile. A durable write whose guard stopped authorizing it also bars further writes (reported with the guard's `session-changed` code).
* **The legacy ledger `plc.encounters.v1`** is classified in the production key table and the inventory (user, format 1: the plain encounter layer, `chat/encounters/`, owns it and a snapshot from a build that writes it exists), and the vault still never admits it. Its hold:  `reconcileRaw` holds it (`legacy-encounters`), `createAndMigrate` neither copies nor verifies nor lists it (`heldLegacy`), and `appLocal` refuses writes and removal of it; raw bytes and an existing private copy in the vault are preserved and readable. Tests apply the classification to a scratch copy of the modules.

## What this engine does NOT do yet (stated plainly after the independent review, T895)

* **Deletion is cryptographic only after compaction, and nothing in the app compacts.** A typed removal emits `thread.del` and `key.destroy` and writes the new state in one projection that removes no records (`removeUpTo` is 0), so the DEK-sealed `key.put` record that holds the chat's raw key, and the owner-sealed `owned.put` records, STAY IN THE LOG until `compact()` rewrites it. Until something compacts, "deleting a chat cryptographically deletes its derived records" is not true in the product. Who compacts, and when, is board task T896 (it blocks the acceptance of attributed encounter records, T418).
* **Compaction is fenced by exact bytes (T895 finding 1).** `compact()` first reads the stored vault and requires it to be what this session holds (same state, same last seq): a stale session is refused with `stale-session`, so a chat another session deleted and compacted cannot come back. The new records then start right after the stored last seq, so a writer that slips in between that read and the replace collides on the exclusive add (`conflict`, nothing replaced). An unknown adapter outcome is settled by reading the stored log (replaced = reported, not replaced = the numbers are given back, anything else bars the next write until `reconcileChatProjection`).
* **The header rewriters are fenced too (finding 2).** `changePassphrase`, `addWrap` and `removeWrap` rewrite the header as one atomic projection compared with exactly the header and log they read, and refuse with `busy` when anything changed; storage that cannot compare is refused (`unsupported-adapter`) once the vault holds typed records. They used to read, await crypto and write blind, which could replace `plc-vault/2` by a stale `plc-vault/1` and make typed data unreadable.
* **The writer guard is the caller's.** Every guard is optional (no guard means authorized) and `delDoc` takes none; the engine never compares `logical.rev` or `logical.epoch` (it records what the plan supplies). The fence is the caller's guard function (the app's lease and epoch, `chat/vault/vault-store.mjs`) plus the exact-bytes stale-base compare. The tests use `() => true` or a counter, never a real writer lease.
* **`compact()` and the unsupported-event rule:** an old known-key session can still compact (unchanged).

## Not done here (open gates)

* No feature producer and no typed writer data from a real producer: a genuine semantic-2 snapshot (both stores) must be captured from the actual producer later; the data snapshot suite and `plc.encounters.v1` classification wait for that.
* No host, UI, import, backup or export change; turning the vault off or exporting must still refuse when it cannot hand over sole typed state (consumer work).
* No claim that encrypted state is safe under arbitrary multiple writers: ordering rests on the engine queue plus the exclusive lease, and the exact-bytes comparison in the transaction turns every other writer into a refusal.
* Old readers are not protected: the frozen reader is shown to refuse semantic 2 on both unlock paths, but an old known-key session can still compact. That limit is unchanged.
* Existing private copies of encounter text under the vault key cannot be retroactively erased.
